# ADR — 가족 문화체험의 주요 결정

이 문서는 선택의 배경·대안·이유·영향을 기록한다. 목적은 [INTENT](intent/INTENT.md), 요구사항은 [PRD](PRD.md), 현재 구조는 [ARCHITECTURE](ARCHITECTURE.md)를 참조한다. `채택`은 사용자 또는 기존 권위 문서의 결정이며 구현 성공을 뜻하지 않는다. `제안`과 `미결정`은 구현 확정으로 해석하지 않는다. 채택된 결정 변경 시 기존 이유를 덮어쓰지 않고 대체 결정을 추가한다.

## ADR-001 — 관심 분야에서 가족 체험을 발견하는 과업

- 상태: 채택 · 2026-10-07 사용자 인터뷰.
- 배경: 사용자는 부모·자녀 등 가족 구성원의 체험 발견 어려움을 핵심 문제로 선택했다. 이후 관심 분야는 있지만 가족에게 맞는 체험을 찾기 어려운 상황에 동의했다.
- 검토한 대안: 무엇을 할지 모르는 사용자의 아이디어 탐색, 관심 분야 내 체험 발견, 참여 가능 여부 확인 중심 서비스.
- 결정 이유: 관심 분야와 가족 상황을 여러 자료에 대조하면서 추가 조회·질문·대안 선택이 필요한 과업으로 구체화할 수 있다.
- 영향: 문화 내용과 관심 분야의 연결을 추천에 포함한다. 참여조건 검증은 추천 신뢰성을 뒷받침한다. 실제 사용자 효과와 에이전트 이득은 별도로 검증한다.

## ADR-002 — 비교할 후보 제공

- 상태: 채택 · 2026-10-07 사용자 인터뷰.
- 배경: 체험 발견 이후 서비스가 어디까지 결과를 만들어야 하는지 정할 필요가 있었다.
- 검토한 대안: 후보 몇 개를 비교·선택하도록 제공, 여러 체험을 엮은 일정 제공.
- 결정: 사용자가 직접 선택할 후보 몇 개를 제공한다.
- 결정 이유: 사용자가 전자를 명시 선택했다. 별도의 일정 최적화 필요성은 확인되지 않았다.
- 영향: 일정 구성·자동 예약으로 범위를 확대하지 않는다. 후보 개수와 비교·정렬 세부사항은 PRD에서 정한다.

## ADR-003 — 데이터 충분성에 따른 초기 범위

- 상태: 채택 · 2026-10-07 사용자 조건부 결정과 공식 자료 확인.
- 배경: 다른 지역·현대 한국문화까지 포함할지에 대해 사용자는 기존 API의 충분한 자료 확보를 조건으로 제시했다.
- 검토한 대안: 전국·현대 한국문화까지 확장, 서울의 전통문화·역사 체험에 집중.
- 결정: 현재는 후자. [범위 조사](product/data-sources.md#지역과-문화-범위)에서 확장에 충분한 현재 API 자료를 확인하지 못했다.
- 영향: 다른 지역 자료가 전혀 없거나 확장이 불가능하다고 주장하지 않는다. 지역·주제별 유효 후보와 API 반환 근거를 확보하면 범위 변경을 다시 결정할 수 있다.

## ADR-004 — 모델과 에이전트 구성

- 상태: 제안 · 기존 에이전트 설계에서 이관.
- 후속 결정: 에이전트 형태·도구·개발 스킬은 ADR-012로 구체화했다. 실제 모델 ID·endpoint·버전·연결 검증은 남아 있다.
- 배경: 조건의 자유서술과 자료 충돌을 해석하고 다음 도구를 선택할 실행 구조가 필요하다.
- 제안: 단일 Nemotron/NIM + NAT 에이전트와 코드 검증기를 사용한다. 날짜 계산·형식·예산 제어는 코드가 맡는다.
- 대안과 검토 상태: 단순 필터는 비교 기준으로 사용한다. 다중 에이전트·Retriever/MCP는 필요가 확인될 때 검토하며 채택하지 않았다. 특정 대안의 우월성이 입증된 상태는 아니다.
- 채택 전 확인: 접근 가능한 모델/endpoint·NAT 버전, 실제 도구 호출과 결과 검증, 정책 내 지연·호출량, 상황에 따른 다음 행동 변화.
- 영향: 현재 문서는 구체 SDK·모델 ID·함수명·버전을 확정하지 않는다.

## ADR-005 — OpenShell 실행 경계

- 상태: 적용 필수 · 기존 공식 미션과 저장소 실행 지침.
- 배경과 근거: [공식 미션](operations/mission.md)은 OpenShell 구성요소 및 공통 테스트를 요구한다. 기존 제품 설계는 실제 에이전트·도구를 경계 안에서 실행하도록 정했다.
- 결정: 실제 도구 실행을 정책으로 제한하고 허용/금지 접근을 실측한다.
- 대안의 지위: 모델에 금지 지시만 주거나 호스트 도구로 우회하는 방식은 이 경계의 대체안으로 인정하지 않는다. 의무 조건이므로 사용자 기술 취향에 따른 선택 기록으로 포장하지 않는다.
- 영향: 정책 파일 존재·설치·금지 파일 미배치만으로 성공을 주장하지 않는다. 공개 API 호출의 개인정보 의미·요청 소유권은 애플리케이션에서도 검증한다.

## ADR-006 — 웹 스택·배치·저장

- 상태: 일부 해소 · 웹 스택은 ADR-008로 결정; 배치·저장은 미결정.
- 배경: 데스크톱 웹 사용과 외부 사용자 테스트 방향은 있으나 구체 기술·배치·상태 저장 계약은 정해지지 않았다.
- 기존 대안: AWS 웹/API + Brev 에이전트, AWS 에이전트 + Brev GPU 도구, 단일 호스트. 근거와 제약은 [배포 조사](playbooks/aws-brev-deployment.md)를 참조한다.
- 남은 입력: AWS/Brev 역할, 로그인·보존·복구 요구, 예산·동시 사용자 목표. 웹 스택 선택은 사용자 위임에 따라 ADR-008에서 결정했다.
- 영향: 현재 구조도는 논리 책임을 표현한다. 저장·인증 요구를 임의로 확정하지 않으며 자원 생성·비용 집행은 별도 범위다.

## ADR-007 — 조건 미정 상태의 후보 탐색 허용

- 상태: 채택 · 2026-10-07 PRD 인터뷰.
- 배경: 날짜·가족 조건을 모두 정하기 전에도 관심 분야의 체험을 발견할 수 있어야 하는지 확인했다.
- 검토한 대안: 모든 날짜·가족 조건 입력 후 후보 제공, 후보를 먼저 제공하고 미확인 조건 표시.
- 결정: 사용자가 후자를 선택했다.
- 영향: 검색에 사용하지 못한 조건을 충족으로 표시하지 않는다. 초기 탐색 후보와 참여조건을 확인한 추천을 구분하고, 조건 입력 후 관련 판정을 갱신한다.

## ADR-008 — React 웹과 Python API

- 상태: 채택 · 2026-10-07 사용자 스택 선정 위임. ADR-006의 웹·백엔드 미결정을 해소한다.
- 배경: 선택 카드·후보 비교·실행 상태를 표현하고, 추후 네이버 지도를 추가하며 기존 Python 에이전트 설계와 연결해야 한다. 사용자 역할 분담에 따른 언어 제한은 없다.
- 결정: React + TypeScript + Vite, 기존 NVIDIA UI CSS, Python + FastAPI + Pydantic을 사용한다.
- 대안: Next.js + Python API, Python 중심의 간단한 시연 UI, TypeScript 단일 서버. 이는 이번 설계에서 비교한 선택지이며 모두 구현해 성능을 비교한 결과는 아니다.
- 이유: 현재 요구에는 서버 렌더링·검색엔진 노출이 없어 Vite 클라이언트 앱으로 충분하다. React에서 카드·지도 상태를 관리하고 Python에서 NAT 연결과 구조화 데이터 검증을 유지할 수 있다. 단일 TypeScript 서버를 택해도 기존 Python 에이전트 연결은 남는다.
- 영향: 프런트/백엔드 계약 검사가 필요하다. 지도는 공식 JavaScript API를 직접 연결하는 방향으로 준비하며 특정 React 래퍼를 미리 도입하지 않는다. 로그인·이력 요구가 정해지기 전 DB와 인증을 임의 선택하지 않는다.
- 근거: 공식 문서 링크와 실제 연결 전 확인 사항은 [채택한 기술 스택](ARCHITECTURE.md#채택한-기술-스택)에 둔다. 이 선택은 현재 범위에 대한 설계 판단이며 성능상 최적이라는 실측 주장이 아니다.

## ADR-009 — 선택 카드 입력과 로그인 제외

- 상태: 채택 · 2026-10-07 사용자 인터뷰.
- 배경: 사용자는 채팅 인터페이스의 구현 부담을 줄이고 해커톤에서 핵심 체험 발견에 집중하기를 원했다.
- 검토한 대안: 선택 카드만 제공, 직접 입력을 보조한 선택 카드, 채팅 입력; 로그인 도입 또는 로그인 제외.
- 결정: 사용자 입력·추가 질문 응답은 선택 카드만 사용한다. 직접 입력 보조와 회원가입·로그인은 MVP에서 제외한다.
- 영향: 카드 방식에도 구조화 출력 검증은 필요하다. 사용자 계정 없이 요청별 접근 경계를 유지한다. 로그인 제외만으로 결과 저장·보존·재방문 복원까지 제외한 것으로 해석하지 않으며 해당 범위는 별도로 확인한다. ADR-006의 로그인 미결정을 해소하고 ADR-008의 입력·접근 범위를 구체화한다.

## ADR-010 — 현재 탐색에 집중

- 상태: 채택 · 2026-10-07 사용자 인터뷰. ADR-009에서 남긴 결과 복원·이력 기능의 범위를 해소한다.
- 배경: 사용자는 해커톤 수준에서 핵심 MVP에 집중하기를 원했다.
- 검토한 대안: 현재 탐색에서만 결과 이용, 재방문 결과 복원·검색 이력·찜 제공.
- 결정: 현재 탐색에서 조건을 수정하고 체험 후보를 비교·선택하는 흐름만 제공한다. 재방문 결과 복원·검색 이력·찜은 제외한다.
- 영향: 해당 부가 기능을 위한 계정·영속 이력 저장은 도입하지 않는다. 실행 중 작업 상태·익명 요청 격리·일일 호출 예산·공통 테스트 산출물까지 없애는 결정은 아니다. 운영 데이터의 저장·정리 방식은 실제 배치에 맞춰 정한다.

## ADR-011 — 공통 테스트용 CLI와 공유 실행

- 상태: 대체됨 · 2026-10-07 사용자 결정의 변경을 ADR-013에 반영. 아래는 당시 선택의 기록이며 현재 웹 진입점을 CLI 필수로 해석하지 않는다.
- 배경: 카드 전용 가족 서비스로는 공통 요청과 심사 중 추가 조건을 모두 표현하기 어렵다. 제품 기능을 확대하지 않고 공식 공통 테스트를 실행할 진입점이 필요하다.
- 검토한 대안: 제품에 채팅·일반 요청 화면 추가, 별도 테스트 전용 에이전트 구현, 입력·출력만 분리한 CLI에서 같은 실행 계층 사용.
- 결정: 공통 요청 파일·추가 조건을 받는 CLI를 두고, 모델 호출·근거 판단·도구 검증·예산·OpenShell 실행을 제품과 공유한다. 결과는 공통 요청의 목적에 맞춰 output에 저장한다.
- 이유: 카드 중심 MVP를 유지하면서 제품과 테스트의 판단·안전 구현이 분리되는 것을 막는다. CLI는 팀의 실행 방식이며 주최 측이 요구한 특정 도구나 출력 형식이 아니다.
- 영향: ADR-009의 카드 전용 입력은 제품 웹에 적용한다. 실제 정책 거부는 모델의 거절과 구분해 검사하며, 네트워크 검증에는 통제된 목적지와 합성 데이터만 사용한다. 계약은 ARCHITECTURE, 수용 기준은 PRD C01–C05에 둔다.

## ADR-012 — 단일 ReAct와 제한된 자료 도구

- 상태: 구현 기준 채택 · 2026-10-07 사용자의 에이전트·도구·스킬 조합 우선 확정 요청에 따른 기술 선택. 모델 연결·설치·통합 성공은 미검증.
- 배경: 공식 상세 안내의 연령·동반·운영일 조건과 API 요약이 충돌하거나 누락될 때, 관측 후 추가 조회·질문·대안·종료를 선택해야 한다. 제품과 공통 테스트는 같은 판단·검증·예산 계층을 사용한다.
- 결정: 기존 Brev VM의 OpenShell sandbox에서 단일 NAT `react_agent`·자료 도구·Python/Pydantic 검증기를 실행하고, 모델은 hosted Nemotron/NIM을 호출한다. 자료 도구는 Python NAT 함수로 직접 등록한다. 구체 도구 책임과 개발 스킬은 [구현 기준 조합](ARCHITECTURE.md#구현-기준-조합)에 둔다.
- 대안: NAT Tool Calling, 고정 Sequential Executor, 전문 에이전트 분담. 공식 ReAct 문서는 도구 사이의 관측·판단 반복을 설명하므로 현재 요구에 맞는 출발점으로 선택했다. 여러 역할을 나눌 만큼 독립된 전문 과업은 아직 확인하지 않았다. 성능 비교나 품질 우위가 실측된 결정은 아니다.
- 영향: ReAct 응답 파싱 실패·추가 호출·지연을 검증해야 한다. 모델의 내부 추론을 UI·로그에 그대로 내보내지 않고 실제 도구 실행·판정 근거·종료 사유만 표시한다. 모든 파싱 재시도·숨은 provider 재시도에도 공통 호출 예산을 적용한다.
- 도입 범위: MVP에는 전문 다중 에이전트·장기 메모리·벡터 DB·전체 RAG Blueprint·MCP 서버·별도 Guardrails를 추가하지 않는다. 현재 자료는 API·HTML·공통 파일 도구와 검증기로 처리하고, 실제 자료 추출 실패가 확인될 때 추가 구성의 필요성을 재검토한다.
- 실행 환경 검토: 사용자가 확인한 기존 `finals-bridge`는 2 CPU·8GB RAM·GPU 없음이며, [연결 시험 문서](playbooks/aws-brev-deployment.md#12-모델-없는-연결-시험-구현)도 같은 환경을 기록한다. Brev에서 에이전트를 실행하는 것과 Brev에서 모델을 직접 서빙하는 것은 별개다. 현재 VM은 GPU를 요구하는 NVIDIA NIM LLM의 로컬 서빙 조건을 충족하지 않으므로 hosted 연결을 첫 구현 기준으로 선택한다. 새 GPU 자원 생성이나 비용 집행은 이 선택에 포함하지 않는다.
- 남은 확인: 현재 사용할 수 있는 Nemotron 모델 ID와 endpoint, 해당 모델의 한국어 조건 해석·ReAct 파싱·실제 도구 실행, 배포 호스트의 NAT/OpenShell 버전, 서울 API의 sandbox 내부 연결. 개발 호스트의 정식 인증 조회는 자료 근거 문서에 기록한다. 실패 시 같은 성공으로 기록하거나 자동으로 다른 agent·모델을 채택하지 않는다.
- 근거: [NAT ReAct](https://docs.nvidia.com/nemo/agent-toolkit/latest/components/agents/react-agent/react-agent.html), [NAT Tool Calling](https://docs.nvidia.com/nemo/agent-toolkit/latest/components/agents/tool-calling-agent/tool-calling-agent.html), [NIM LLM 실행 조건](https://docs.nvidia.com/nim/large-language-models/1.14.0/getting-started.html), [자료 근거](product/data-sources.md). 공식 NAT latest의 표시 버전은 1.8이며 준비 자료의 예선 설치 기준 1.9.0과 다르므로 실제 설치 schema를 우선한다. 확인일 2026-10-07.

## ADR-013 — 웹 테스트·챌린지 모드와 공유 실행

- 상태: 채택 · 2026-10-07 사용자 결정. 이번 작업은 문서만 갱신하며 프런트·백엔드 구현은 포함하지 않는다.
- 배경: 사용자는 사전 선택·분석 결과의 짧은 재생 시연과 제공 파일을 실제 처리하는 공통 테스트를 웹에서 구분하고 싶어 한다. 공식 요건은 제공 파일의 실제 처리와 OpenShell 경계이며, 특정 모드 화면이나 CLI를 요구하지 않는다.
- 검토한 대안: CLI를 공통 테스트의 주 진입점으로 유지, 기존 가족 화면에 공통 요청을 섞기, 기존 화면 요소를 재사용한 별도 웹 모드 제공.
- 결정: 테스트 모드는 사전 선택과 해당 분석 기록·결과를 약 2~30초에 재생한다. 챌린지 모드는 요청·추가 조건을 공유 실행 계층에 전달하고 실제 작업 기록·결과를 표시한다. CLI는 필요할 때 보조 실행 방법으로 유지할 수 있으나 새로 구현해야 할 필수 기능이 아니다.
- 이유: 웹에서 두 시연 목적을 구별하고 심사 중 새로운 조건을 전달할 수 있으며, 가족 카드 흐름과 챌린지의 일반 요청·코스 초안 형식을 각각 유지한다.
- 영향: ADR-011의 CLI 중심 진입점을 대체한다. ADR-009의 카드 전용 입력은 가족 체험 찾기에 적용하고 챌린지 요청·추가 조건 입력은 개발·심사용 예외로 둔다. ADR-010의 이력 제외와 ADR-012의 단일 에이전트·공통 검증·예산·OpenShell 경계는 유지한다.
- 실행 구분: 합성 기록은 mock, 과거 실제 기록은 replay, 현재 실제 처리는 live로 구분한다. 압축 재생은 실제 분석 시간·정책 차단의 증거가 아니며, 실제 챌린지에 동일한 시간 상한을 강제하지 않는다. 연결 전에는 미실행을 표시하고 결과를 합성해 성공으로 대체하지 않는다.
- 구조·검증: 웹은 입력 전달과 표시, 백엔드는 실행별 요청·작업 상태 관리, OpenShell 내부 에이전트·도구는 허용 자료 읽기와 output 저장을 맡는다. [ARCHITECTURE](ARCHITECTURE.md#웹-모드와-공통-테스트-실행)의 구조와 [PRD](PRD.md#테스트-모드와-챌린지-모드)의 수용 기준으로 확인한다.
