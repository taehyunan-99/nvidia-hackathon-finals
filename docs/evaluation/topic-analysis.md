# 예선 주제에서 도출한 선정 원칙

2026-10-05 조사. 예선 Bio-3 저장소 `52f6be29e432b1fa660e2a9b3b6b7556d04793d4`의 문서·코드를 읽기 전용으로 확인했다. 실제 서비스·모델·GPU를 이번에 재실행하지 않았다. [예선 구현 근거](bio3-review.md)를 토대로 주제 선택을 분석하며 구현 평가·과거 점수는 변경하지 않는다.

## 결론과 증거의 범위

확인할 수 있는 적합성은 **자료가 서로 다른 항체 후보를 비교하는 업무에, 자료 확인→필요한 계산 선택→검증→근거와 미확인 제시가 들어맞는다는 것**이다. 생물학이라는 분야 자체보다 문제의 구조가 중요하다. 사용자는 이번 조사에서 평가 피드백이 없고 주제의 영향도 모르며 오히려 감점 요인이었을 수 있다고 확인했다. 따라서 **본선 진출을 좋은 주제의 정답 라벨로 사용하지 않는다.**

| 근거 구분 | 확인한 내용 | 말할 수 없는 내용 |
|---|---|---|
| 현재 공식 공개 안내 | 목표에 따른 계획·도구 호출·산업 문제 해결과 NVIDIA 스택을 강조 [O1] | 상세 배점·본선 심사 항목·특정 기술 개수 의무 |
| 프로젝트 사실 | 재사용/예측/보류 설계, 상태별 도구 제한, 실제 실행을 기록한 문서 [P1–P4] | 이번 조사에서 현재 원격 서비스가 성공했다는 주장 |
| 과거 내부 시험 | 규칙 최종 상태 8/8, 복구 후 모델 완주 6/6, 새 항체 2건 접촉 F1=0 [P3] | 새 항체 전반의 정확도·결합력·치료 효능 |
| 사용자 확인 | 본선 진출·서비스/GitHub 중심 제출의 기존 기록; 이번 대화에서 도구 탐색→ADC 고려→범위 축소→HER2 선정 경위 확인 | 정확한 제출 commit·심사위원 열람 경로·주제의 가점/감점 |
| 팀의 추론 | 공식 지향점과 프로젝트 강점의 연결, 아래 주제 패턴·배점 제안 | 실제 합격 인과·입상 확률 |

공식 페이지를 다시 열고 평가 기준을 검색했지만 상세 심사표는 확보하지 못했다. 공식 신청 폼은 이번 웹 도구에서 접근 불가였다. 저장소의 9월 20일 폼 기록은 문제·솔루션·기술 스택 제출을 설명하지만 예선 배점 원문을 제공하지 않는다. 공개된 적 없다고 단정하지 않으며 다른 행사의 심사표로 메우지 않는다.

## 실제 선정 과정과 당시 기준

사용자의 설명에 따르면 NVIDIA의 바이오 도구·스킬이 많다는 점이 탐색의 출발이었다. ADC도 고려했지만 해커톤에서 구현하기 어렵다고 판단해 에이전트 수준에서 완성 가능한 HER2 후보 검토로 좁혔다. ADC의 어떤 세부 설계들을 비교했는지는 이번에 읽은 후보 문서에 남아 있지 않아 사용자 설명 이상의 순서를 만들지 않는다.

예선 저장소의 [문서 이관 기록](https://github.com/taehyunan-99/nvidia-hackathon/blob/52f6be29e432b1fa660e2a9b3b6b7556d04793d4/docs/references/document-selection.md)을 따라 원래 조사 저장소의 17·19·24번 문서를 확인했다 [H1–H3]. 25개 후보 조사와 후보 선정 논의안은 팀 저장소 이관 때 제외됐고 원본에 남아 있었다.

| 기록 | 당시 판단 | 이번 해석 |
|---|---|---|

| 19번 25개 후보 조사 | 특정 연구 직무·실제 문제의 문헌 근거·BioNeMo의 핵심 기여·상태별 행동·확인할 산출물·공개 자료 평가 | 연구 도구를 연결할 수 있다는 가능성과 실제 효용을 구분했음 |
| 19번 우선 6개 비교 | 도킹 검증·바인더 환경 검토·대조군 설계·내성 변이·작용기전 감사·fragment 설계 | 특정 한 후보의 압도적 우위를 증명한 순위표가 아니었음 |

당시 기준이 없었던 것이 문제가 아니다. **기준의 질문을 실제 증거와 탈락 판단으로 얼마나 강제했는지**가 다음 개선 지점이다. 도구가 많으면 조합 탐색 비용을 줄일 수 있지만 그 사실이 사용자 문제의 중요성·API 접근·에이전트 이득을 보장하지 않는다. 새 루브릭은 기존 질문에 증거 수준·관문·기준선·미확인 처리·중단 조건을 붙인다.

## 유리했을 가능성과 불리했을 가능성

본선 진출이라는 결과 하나만으로 주제·구현·제출물의 효과를 분리할 수 없다. 같은 팀이 다른 주제를 냈을 때의 결과도, 같은 주제를 더 단순하게 냈을 때의 결과도 없다. ‘주제는 약했지만 구현이 보완했다’, ‘주제와 구현 모두 좋았다’, ‘주제 영향은 작았다’는 설명이 모두 남아 있다.

| 선택의 특징 | 가능한 이점 | 가능한 불이익 / 다음 검증 |
|---|---|---|
| 도구가 많은 바이오 분야에서 시작 | 도메인 계산과 NVIDIA의 연결을 찾기 쉬움 | 공급된 도구에 맞춰 문제를 만들 위험; 사용자 작업 자료로 수요 확인 |
| ADC에서 검토 업무로 축소 | 산출물과 검증 경계를 작게 만들 수 있음 | 축소 뒤 남은 가치가 전문가에게 충분한지 확인 필요 |
| 전문적인 구조 비교 | 근거와 결과를 시각적으로 연결 가능 | 심사자에게 도메인 설명 부담이 큼; 무엇을 끝냈는지 짧게 이해 가능한지 확인 |
| 불확실성·보류를 정직하게 표시 | 과장을 막고 후속 질문을 남김 | 결과가 대부분 보류면 가치가 약함; 완료할 수 있는 핵심 결정 비율 확인 |
| 여러 도구·복잡한 실행 | 하나의 검토 흐름을 보여줄 수 있음 | 연결·정확도·지연 위험 증가; 같은 도구를 쓰는 단순 기준선과 비교 |

이 표의 불이익도 실제 감점 사실은 아니다. 다음 주제에서 먼저 확인할 위험 가설이다.

## 예선의 무엇이 잘 맞물렸는가

| 주제에 내재된 특성 | 에이전트와 도구의 역할 | 프로젝트가 보여준 가치 | 남은 검증 |
|---|---|---|---|
| 후보마다 자료 종류·완전성이 다름 | 조회 결과를 읽고 공개 복합체 재사용/새 예측/보류 선택 | 동일 버튼으로 실행해도 자료 상태에 맞는 경로 | 모델 선택이 고정 규칙보다 나은지 |
| 그럴듯하지만 다른 후보의 구조일 수 있음 | 서열·사슬·분석 구간 검사를 통과한 근거만 사용 | 잘못된 비교를 계산 이전에 차단 | 실제 연구자가 겪는 빈도·절감 시간 |
| 예측은 유용하지만 비용·지연·오차가 있음 | 충분한 공개 근거는 재사용, 필요한 경우만 Boltz-2 | NVIDIA 예측을 문제상 필요한 지점에 연결 | 비용/정확도 기준선 대비 순이득 |
| 관측·계산·누락이 동시에 존재 | 비교 가능한 항목만 보고하고 나머지는 보류·후속 질문 | 모르는 것을 0이나 안전함으로 바꾸지 않음 | 보류가 과도하지 않은지, 다음 결정에 실제 도움이 되는지 |
| 결과의 공간적 근거를 확인할 수 있음 | 구조·지표·출처·보고서를 연결 | 사용자가 결과를 검토할 구체적인 대상이 남음 | 화면 열람이 판단 정확도를 높이는지 |

이 역할 분담에서 Nemotron은 허용된 다음 도구를 선택하고, NAT는 도구 실행을 연결하며, 구조 계산과 유효성 검사는 코드가 맡는다. 모델이 원자 계산·입력 안전성·최종 과학적 진실을 모두 판단했다고 설명하면 안 된다. `allowed_tools`는 입력 확인·조회·계산·제출의 많은 단계에서 도구를 하나로 제한한다 [P2]. 따라서 모델의 실질적인 선택 공간은 코드가 허용하는 일부 분기에 있다.

공식 문구와 직접 맞닿는 것은 산업 문제, 목표를 위한 도구 실행, NVIDIA의 실질적 사용이다 [O1]. 근거의 추적 가능성·보류·검토하기 쉬운 서비스는 이를 설득력 있게 드러내는 내부 품질 강점이다. 후자를 확인된 공식 가점이라고 부르지는 않는다.

## 에이전트 적합성과 에이전트 우위는 다르다

재사용/예측/보류가 존재한다는 사실은 상태 의존 업무의 증거다. 그러나 그 분기가 몇 개의 확정된 조건으로 완전히 결정되면 규칙 엔진으로 충분할 수 있다. 예선 규칙 비교군도 같은 8개 입력의 최종 상태를 맞혔다. 다만 직접 권장 경로는 4/6이었고, 부족 입력 두 건은 예측 진입 후 검사에서 보류했다 [P3]. **결과 일치·경로의 적절성·외부 호출 낭비는 별도 지표**다.

본선에는 ‘LLM을 빼면 무엇이 실제로 불편해지는가’를 물어야 한다. 입력마다 용어·근거의 위치가 달라지거나, 조회 결과의 누락/충돌에 따라 질문과 탐색 대상을 바꾸거나, 사용자 제약에 따라 검증할 항목을 선택해야 한다면 이득 가설을 만들 수 있다. 이는 앞으로 확인할 후보 조건이며 Bio-3가 이미 전부 구현했다는 뜻이 아니다.

고정 워크플로와 유연한 도구 선택을 구별하고 가장 단순한 대안부터 비교하는 원칙은 외부 에이전트 설계 자료와도 일치한다 [M1]. 모델을 제거하는 비교는 예측·검색 도구 자체를 제거하는 비교와 다르다. 같은 도구·데이터를 제공한 규칙/단일 호출 대비를 해야 오케스트레이션의 기여를 볼 수 있다.

## 좋은 주제에 반복되는 구조

분야 대신 다음 다섯 가지를 찾는다. 아래는 예선 한 사례와 설계 원칙에서 도출한 **검증할 가설**이며 수상작 전체를 분석한 통계적 패턴이 아니다.

| 패턴 | 잘 맞는 이유 | 부적합해지는 경계 |
|---|---|---|
| 명확한 사용자와 좁은 결정 | 완료 상태·실패 비용을 정의할 수 있음 | ‘산업 혁신’만 있고 무엇을 끝내는지 없음 |
| 도구 결과를 보기 전에는 다음 행동을 전부 정하기 어려움 | 수집 결과를 받아 탐색·검사를 조정할 이유가 있음 | 항상 같은 호출을 같은 순서로 수행 |
| 정보는 부족해도 결과는 확인 가능 | 찾아내는 과정은 어렵지만 출처·수치·상태로 검산 가능 | 생성한 설명의 그럴듯함만으로 정답 판정 |
| 이질적인 근거를 하나의 결정에 연결 | 단순 검색 이후의 대응·충돌 해소·후속 작업이 가치 | 문서 요약만으로 사용자 목적이 이미 충족 |
| 작게 닫히는 실행 범위 | 정상·변화·실패를 짧게 시연하고 복구 가능 | 학습·실험·외부 승인 등 장기 의존성이 핵심 |

특히 ‘어렵게 만들 수 있는 문제’보다 ‘어려운 부분을 작은 입력으로 확인할 수 있는 문제’가 유리하다. 수일짜리 실험으로만 판정 가능한 주제는 중요하더라도 7시간 선정 후보로는 위험하다. 복잡한 산업 전체보다 하나의 검토·진단·대조 업무를 고른다.

## 예선에서 반복하지 않을 것

첫째, 구조 예측 품질과 에이전트 실행을 혼동하지 않는다. 과거 새 항체 두 건에서 표적 접촉 F1=0이었어도 호출 복구 후 흐름은 6/6 완주했다. 구조 근거 검토라는 제한된 목표는 가능하지만 결합력·효능 순위로 넓히면 완료를 검증할 수 없다 [P3, P4].

둘째, 검색할 수 있는 공개 근거를 못 찾아 예측하는 것은 기술 사용이 늘어도 가치가 늘었다는 뜻이 아니다. 초기 평가의 제한된 카탈로그와 후속 공개 구조 조회 개선을 구분한다 [P3, P5]. 본선에서는 먼저 확보 가능한 근거와 가장 싼 도구부터 확인한다.

셋째, 완성된 예선의 기능 수를 주제 잠재력 점수로 복사하지 않는다. 예선은 3명·누적 구현, 본선은 2명·7시간이다. 배포·DB·복원·3D를 모두 가져오는 것이 선정 기준이 되어서는 안 된다. 첫 연결·검증을 끝낼 최소 범위가 별도로 필요하다.

## 주제 선정 루브릭으로의 연결

항목·배점·등급·관문·판정식은 [선정 기준](topic-selection.md)에서만 관리한다. 이 분석은 사용자 문제·에이전트 이득·자료·검증·구현 범위가 왜 중요한지 설명하며 별도 점수표를 만들지 않는다.

Bio-3에 역으로 높은 총점을 부여하지 않는다. 사용자 문제와 실제 자료·분기·검토 산출물은 확인되지만 실제 사용자 효용, 규칙 대비 추가 이득, 본선 시간 내 재구현 가능성은 별도 증거가 필요하다. 특히 agency 4의 비교 이득은 기존 8/8 결과로 충족되지 않는다. 신규 API 접근과 시간 예산도 과거 성공으로 현재 통과시키지 않는다.

[주제 선정 스킬](../../.agents/skills/topic-rubric/SKILL.md)은 선정 기준의 항목·등급·관문·unknown 처리·반례와 입력 계약을 사용한다. 먼저 이 기준으로 후보를 비교하고, 최종 선택 후에는 기존 구현 루브릭으로 실행 품질을 평가한다. 하나의 점수로 주제 매력과 구현 완성도를 합치지 않는다.

## 확인된 동기와 남은 사실

도구 탐색에서 시작한 동기·ADC 고려와 범위 축소·심사 피드백 없음은 사용자에게 확인했다. 팀의 구체적인 도메인 경험, 실제 사용자 접촉, 최종 비교표·선택 회의의 상세 과정, 정확한 제출본은 미확인이다. 이 사실이 없어도 잠정 선정 기준은 만들 수 있지만 실제 전문가 수요나 심사자의 칭찬을 만들어낼 수는 없다.
