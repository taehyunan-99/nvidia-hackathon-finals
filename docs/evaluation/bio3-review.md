## 판단

가장 설득력 있는 가설은 **구체적인 산업 문제를 NVIDIA 모델/도구의 상태별 선택으로 해결하고, 그 과정을 배포 서비스와 코드에서 확인할 수 있게 만든 점**이 대회 지향점에 잘 맞았다는 것이다. 주제 자체의 희소성이나 NVIDIA풍 색상이 합격 원인이었다고 판단할 자료는 없다.

이는 선정 원인의 추정이다. 합격 사실만으로 '어떤 항목에서 몇 점을 받았는가'나 다른 참가팀 대비 우위를 역산할 수 없다. 아래의 높음/중간은 관찰된 프로젝트와 대회 문구의 연결 강도이며 선정 확률이 아니다.

공식 행사 소개는 산업 문제·목표에 따른 계획·도구 호출을 강조한다. 상세 배점과 심사평은 확보하지 못했으므로 다른 대회의 평가표를 이 대회 기준으로 적용하지 않는다.

## 선정에 기여했을 가능성이 큰 요소

| 우선순위 | 대회와 맞물리는 지점 | 우리 프로젝트의 확인된 내용 | 심사에서 전달될 수 있는 가치 | 연결 강도 |
|---|---|---|---|---|
| 1 | 산업 현장의 실제 문제 | 항체 후보의 서열·출처·관측/예측·누락 정보를 같은 기준으로 비교 | 누가 무엇을 결정하기 어려운지, 결과를 어디에 쓸지 분명 | 높음 |
| 2 | 목표→판단→도구→완료 | 공개 구조 재사용 / 필요한 예측 / 입력·계산 보류라는 실제 분기 | 입력 상태에 따라 행동이 바뀌는 에이전트임을 보여줌 | 높음 |
| 3 | NVIDIA 스택의 실제 활용 | Nemotron이 도구를 선택, NAT가 실행, Boltz-2가 구조 예측, 고정 스킬 지침·검증 연결 | 기술명 나열을 넘어서 사용 위치와 결과를 추적 가능 | 높음 |
| 4 | 제출 데모를 검토할 수 있음 | 기본 시나리오·진행 표시·3D·근거·보고·다운로드가 연결된 웹 서비스와 소스 | 심사자가 설치/입력 준비 없이 핵심 흐름을 이해하기 쉬움 | 중간~높음: 제출 방식으로 뒷받침되나 실제 열람은 미확인 |
| 5 | 결과를 믿을 수 있는 범위가 분명 | 실험/계산/미확인 구분, 관측되지 않은 값은 unknown, 후보/조건/구조 대응 검사 | 결과를 과장하지 않고 다음 확인 행동을 제시 | 중간: 공식 독립 배점은 확인 못함 |
| 6 | 중단·실패에 대한 구현 완성도 | 상태별 허용 도구, 중복 호출 방지, 429 처리, 부분 결과·저장 복원 | 시연이 끊겨도 원인·남은 결과·다음 행동을 설명 가능 | 중간: 내부 품질 근거이며 심사자의 확인 여부 미상 |

첫 세 항목은 공식 지향점과 직접 연결된다. 뒤 세 항목은 그 가치를 전달하고 작동을 뒷받침하는 구현 강점이다. 두 층을 동일한 '공식 심사 항목'으로 표현하지 않는다.

## 제출 방식 때문에 더 중요해지는 부분

서비스와 GitHub 중심이었다면 첫 화면의 기본 입력·상황 설명, 실제 실행에서의 분기, 결과에서 근거까지의 연결이 주장의 검토 비용을 낮춘다. 특히 기본 시나리오가 예측을 생략하는 사례만이 아니라 **실험 구조와 예측을 함께 비교하는 사례**여서 NVIDIA 예측 사용 지점을 보여줄 수 있었다.

코드에서는 `logic/agent_session.py`의 상태 관문, `logic/nat_workflow.yml`의 도구 등록, `logic/runtime_skill.py`의 고정 스킬/해시 검사, `logic/review_policy.py`의 항목별 근거 연결을 확인했다. 진행 화면은 model/rule 주체와 selected/skipped/failed/held 상태를 구분한다. 사용 기술과 보류 설명이 결과 화면에도 남는다는 점이 단순 구현 수보다 중요하다.

다만 기존 알고리즘·규칙이 많은 부분을 보장한다. 이를 모두 LLM의 자율 판단 능력으로 세지 않는다. '모든 행동을 스스로 계획하는 agent'보다는 **검증된 상태 안에서 다음 도구를 선택하는 agent**가 정확한 설명이다.

## 실행 근거와 해석 한계

| 기록 | 관측 사실 | 해석 경계 |
|---|---|---|

| 과거 모델 benchmark → 호출 복구 후 | 2/6 → 6/6 완주, 429 7회 복구 | 작은 회귀 시험. 후속 회차는 예측 캐시 사용, 새 정확도 검증 아님 |
| 최종 입력/예측 계약 검증 | 공개 구조+가상 변이 한 실행, 약 113.1초, 규칙 복구 0 | 한 입력의 end-to-end 성공 |
| WT+D185A 실제 공개 후보 | 브라우저 접수→NAT/Boltz→저장/결과, 약 128.7초, 규칙 복구 0 | 서열/좌표 대응 확인이며 결합력 검증 아님 |
| WT+D185A+Fab37 | 약 220.8초, 예측+실험 구조 선택+Fab37 계산 보류, 규칙 복구 0 | 구조가 있어도 계산 조건이 부족하면 보류하는 흐름 |
| 결과 연결·운영 검사 | 새로고침 후 동일 실행, JSON/CSV·구조 파일, 세션 격리·별도 볼륨 복원 기록 | 이번에 원격 E2E를 다시 실행한 것은 아님 |

두 실제 공개 후보 실행의 D185A 예측 파일은 같은 해시이므로 독립 정확도 표본으로 중복 집계하지 않는다. 기존 신규 항체 2건의 실험 접촉 대비 예측 F1=0이라는 반례도 유지한다. 코드/검증 기록의 완성도는 과학적 예측 정확도를 보장하지 않는다.


## 본선에서 가져갈 것 / 줄일 것

| 가져갈 원칙 | 7시간에서의 구현 | 과잉 투자 방지 |
|---|---|---|
| 사용자 문제와 완료 기준 | 한 사용자가 한 결정을 끝내는 산출물 | 어려운 도메인 이름·큰 사회적 가치만으로 정당화하지 않음 |
| 상태에 따른 도구 선택 | 정상·변화·자료 부족에서 다른 행동을 보이는 2~4개 도구 | 도구/agent 수 증가를 자체 목표로 삼지 않음 |
| 검증 가능한 결과 | 원문/수치/제약/파일을 검사하는 validator | 검증 불가능한 모델 성능 주장 줄이기 |
| 심사자가 확인하기 쉬운 서비스 | 준비된 입력, 실제 단계, 결과와 근거, 다음 행동 | 도메인에 필요 없는 3D·대형 히어로·복잡한 배포 생략 |
| 실패를 관리하는 실행 | 시간/호출 상한, partial/hold, trace | 예선의 2~4분 실행도 본선 발표에 길 수 있으므로 초기에 측정 |

가장 큰 추가 과제는 **규칙/직접 검색 기준선보다 agent가 왜 필요한가**를 같은 입력으로 보이는 것이다. 예전 benchmark에서 규칙도 최종 상태 8/8을 맞혔으므로 'LLM이 있어서 정확해졌다'는 주장은 아직 지지되지 않는다. 다른 입력에서 도구/질의/자료 수집을 조정하는 이득 한 가지를 검증하는 편이 낫다.

## 루브릭으로 옮기는 방법

[내부 루브릭](rubric.md)의 가중치 **문제 15 + agent 판단 20 + NVIDIA 활용 15 = 핵심 50점**은 공식 지향점에 집중하기 위한 팀 제안이다. 정확성 15, 안정성 10, UX 10, 재현 10, 전달 5는 그 핵심을 검증·시연하기 위한 나머지 50점이다. 공식 배점에서 가져온 숫자가 아니다.

기존 **73.75/100**은 자료 기반 주관적 시범 채점이며 실제 예선 점수·상대 순위·통과선이 아니다. [루브릭 채점 절차](scoring-guide.md)에서 관찰 증거가 있는 등급만 주고 부족한 점수를 다음 작업으로 변환한다.
