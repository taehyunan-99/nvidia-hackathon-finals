# 근거 기반 채점 방법 — v2

## 평가 계약

평가 시작 전에 사용자 과업·산출물·허용 도구·실패/보류 조건·측정 한도를 고정한다. subject는 같은 제품 식별자, revision은 현재 코드의 commit과 변경 파일 hash를 포함한 식별자, environment는 공유 실행 환경/설정 식별자다. 영역별 브라우저/모델/OS 버전은 note에 적는다. 변경된 코드에 과거 통과를 붙이지 않는다.

전체 모드는 design/mock/replay/live/mixed다. 근거가 섞이면 mixed로 선언하고 각 항목의 evidence_mode에는 design/mock/replay/live 중 하나를 쓴다. design은 설계/정적 화면만, mock은 합성 도구나 입력, replay는 저장된 실행 기록, live는 실제 모델/도구를 포함한 실행 근거다. frontend의 mock은 브라우저에서 합성 이벤트를 실제 조작한 평가일 수 있다. 데이터 모드와 브라우저 관측 여부를 혼동하지 않는다.

`evidence_level`은 design(최대 1), implementation(최대 2), observed(최대 4)다. agent의 항목별 evidence_mode 상한은 design 1 / mock 2 / replay 3 / live 4이며 frontend는 design 1, 나머지 4다. 전체 모드가 mixed가 아니면 항목 모드가 전체 모드와 같아야 한다. mixed는 상한 면제가 아니며 항목별로 적용한다. 상한은 자동 부여 점수가 아니다. 정적 스크린샷만 보고 브라우저 조작을 관측했다고 쓰지 않는다. 미실행·자료 부족은 null이며 실행으로 실패를 확인한 0과 다르다.

실모델+합성 도구의 경우 NVIDIA 호출 자체의 기여 항목은 live 근거가 될 수 있지만, 실제 검색의 정확성은 합성 응답으로 live 판정할 수 없다. 하나의 항목에 서로 다른 모드의 필수 조건이 섞이면 가장 약한 필수 근거의 모드를 쓰고 나머지는 note에 적는다. 코드 기반 오류 주입이 실제 실행 경계에서 작동한 경우에는 실제 경계의 관측 범위만 live로 기록한다.

subject/revision/environment 식별이 부족하면 일부 관측이 있어도 정식 숫자 집계를 보류한다. commit이 없으면 변경 파일 hash 등 재식별 가능한 현재 상태를 기록할 수 있다. 임의 식별자를 만들어 검사를 통과시키지 않는다.

## 관측과 등급

항목별 0~4 정수와 `evidence` 경로/실행 ID, `note`의 기대→관측→판정 이유를 기록한다. 등급은 기준의 모든 조건을 충족한 가장 높은 값이며 한 조건이 부족하면 상위 등급으로 올리지 않는다. 복합 항목의 평균을 임의 계산하지 않는다. null/unknown의 note에는 다음에 필요한 확인을 쓴다. pass와 fail 모두 증거가 필요하다.

채점기는 형식·가중치·모드 상한·버전·누락·정수·관문을 검사할 뿐 근거 문자열의 진위를 보증하지 않는다. 평가자는 실제 경로·코드 버전·입력·원본 결과를 읽고 판정한다. LLM 심사만으로 정답을 확정하지 않으며, 가능한 것은 코드 검사/독립 검산으로 확인하고 표현 품질은 브라우저와 사람 관측으로 보완한다.

- agent: 정상, 관측 변화, 자료 부족/충돌, 도구 실패, 부적절한 도구/외부 지시문을 포함한 작은 평가셋을 과업에 맞게 만든다. 정답 경로 하나를 강제하지 말고 허용 결과/제약을 판정한다. 개발에 쓰지 않은 입력과 같은 입력·예산의 규칙/직접 호출 기준선을 구분한다.
- frontend: 같은 이벤트 계약으로 입력 전/진행/완료/보류/실패, 새 실행, 긴 내용, 후보 수 변화, 키보드와 모션 감소를 확인한다. 구현하지 않은 동료의 과업 관측이 없으면 해당 4점 조건은 충족하지 않는다.
- 통합: 동일 subject/revision/environment의 두 영역 채점표와 실제 서비스 경계 관측을 연결한다. 같은 trace를 인용해도 각 영역은 다른 사실을 채점하고 통합에는 점수를 다시 더하지 않는다.

## 경계 사례의 판정

- **1과 null:** 해당 항목의 설계/구현을 읽어 확인했지만 2등급에 필요한 관측이 부족하면 1이다. 해당 항목의 설계/구현조차 확인할 자료가 없으면 null이다. 다른 항목에서 실행을 관측했다는 사실만으로 이 항목을 2로 올리지 않는다. 확인된 결함은 0과 해당 관문 실패 근거로 별도 판정한다.
- **시각 디자인:** 토큰 import·CSS grid·heading 존재만으로 읽기 쉬움과 정렬을 확인한 것은 아니다. design 2에는 현재 코드의 대표 화면을 실제로 보거나, 해당 버전/상태가 식별되는 캡처와 명시적인 시각 관측이 필요하다. 기능 버튼을 눌렀다는 기록만 있으면 시각 기준은 1까지만 근거가 된다.
- **키보드 관문:** critical_access의 핵심 과업은 사전에 정한 시작부터 완료까지의 전체 조작이다. 이 리허설에서는 시나리오 선택→실행/단계 진행→결과/근거 탐색→초기화를 포함한다. Enter로 다음 단계만 완료한 기록은 accessibility 2의 부분 관측이 될 수 있어도 전체 관문 pass의 증거는 아니다. 일부만 확인했으면 unknown이며 실제 막힘을 관측해야 fail이다.
- **조건이 적용되지 않는 경우:** 과업의 데이터형·제품 범위를 실행 전에 기록한다. 불리언 결과에 물리 단위가 없으면 단위 검사는 해당 없음으로 note에 쓰고 값/출처/제약 대응을 확인한다. 선택형 UI에는 자유 텍스트 오타 대신 선택지 로딩 실패·미선택/비활성 처리처럼 같은 실패 위험의 검사를 적용한다. 항목 자체를 삭제하거나 배점을 재정규화하지 않으며, 증거가 부족한 상황을 해당 없음으로 바꾸지 않는다.
- **과거 실행:** trace 파일의 live 표시만으로 현재 구현의 관측이라고 하지 않는다. 실행 당시 코드/설정 식별자 또는 기록된 소스 hash와 현재 범위의 일치 증거가 있어야 현재 평가에 연결한다. 대응이 없으면 참고 기록으로만 두고 현재 항목은 확보한 코드/시험 근거 수준에서 판정한다.
- **합성 시험과 관문:** 영역 관문은 그 영역의 계약을 검증한 합성 시험으로 pass가 가능하며 note에 범위를 명시한다. 실제 도구·모델을 포함한 서비스 연결은 공통 live_path에 별도 증거가 필요하다. 영역 pass를 제품 전체 준비 완료로 옮기지 않는다.

## 측정·표본 원칙

성공 횟수/전체 시도, 잘못된 완료, 올바른 보류, 과도한 보류, 호출 수, 소요 시간, 비용/토큰을 가능한 범위에서 분리한다. 실패 시도·429·timeout을 분모에서 빼지 않는다. 동일 캐시 결과를 독립 정확도 표본으로 세지 않는다. 작은 표본에서는 원시 값과 범위를 보이고 p95·일반화된 정확도를 주장하지 않는다. 기준선 대비 개선은 같은 평가셋·모드·예산에서 확인한다.

대표 반복 3회는 내부 회귀 목표이며 통계적 신뢰성을 보증하지 않는다. 실제 API/GPU 요청은 기존 [모델 정책](../playbooks/model-policy.md)의 승인 범위·호출 상한 안에서만 한다. 부족하면 null/낮은 등급과 관측 한계를 기록한다. 평가 스킬 실행이나 기준 제작 자체는 새 유료 호출 권한이 아니다. 검사는 [CI 원칙](../operations/ci-policy.md)에 따라 변경 영향 중심으로 고르며 10분 초과는 검증 불충분과 대체 확인으로 처리한다.

## 점수와 완료

가중 점수는 `weight × rating / 4`. null은 총점에 기여하지 않되 unassessed_weight로 별도 보고하며 확인된 항목만으로 100점 재정규화하지 않는다. 영역 완료는 80점 이상 AND 모든 항목 3 이상 AND null 없음 AND 영역 관문 전부 pass다. 이 최저 등급은 작은 항목의 심각한 결함이 높은 총점에 가려지는 것을 막는 내부 기준이다.

전체 완료는 두 영역 완료 AND 통합의 모든 관문 pass AND 통합 live 근거다. agent 점수와 frontend 점수를 합하거나 평균하지 않는다. 공식 조건 미제공 unknown은 전체 준비 완료를 보류하지만 다른 구현 작업이나 이 루브릭의 준비 완료를 막지는 않는다.

## 실행과 출력

각 템플릿의 대상/버전/환경을 채우고 항목·관문을 판정한 뒤 `python3 scripts/score.py 채점표.json`을 실행한다. 버전에 따라 기준을 자동 선택한다. integration 채점표의 assessments 경로는 그 파일 기준 상대 경로이며 두 원본 채점표를 다시 계산한다.

평가 결과는 기본적으로 대화에만 보고한다. 파일 저장이 명시 요청된 경우에만 사용자가 정한 위치에 기록하고 기존 채점표를 덮어쓰지 않는다. 임시 계산 입력은 /tmp에 둘 수 있다. 요청하지 않은 완료 보고서·이력 파일을 저장소에 생성하지 않는다.

출력: 대상/버전/모드 → 영역 점수·미채점·최저등급 미달 → 항목별 증거·관문 → 개선 최대 3개와 재검증 조건. 기능 평가와 전체 제품 완료를 구분한다. 관문 결함, 잘못된 결과/거짓 표시, 과업 중단, 나머지 품질 순으로 우선한다. 미확인 항목은 결함이라고 단정하지 않는다.

## 평가자 교정

두 담당이 같은 작은 사례를 독립적으로 채점하고 1등급 이상 차이가 난 항목의 증거/앵커 해석을 맞춘다. 정답이 다른 합리적인 경로를 허용하는지와 반례가 고득점을 막는지 확인한다. 이는 절차이며 아직 수행하지 않은 팀원 교정 결과를 만들어내지 않는다. 앵커/배점을 바꾸면 버전을 올리고 과거 점수와 직접 비교하지 않는다.
