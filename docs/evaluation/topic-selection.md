# 본선 주제 선정 기준

버전: topic-v1 · 2026-10-05. 구현 전 후보를 비교하기 위한 **팀 내부 설계안**이다. 공식 심사표·입상 예측기가 아니며 [agent-v2와 frontend-v2](README.md)의 구현 점수에 합산하지 않는다. 근거는 [예선 주제 분석](topic-analysis.md)에 연결한다.

## 먼저 판단할 것

좋은 후보는 **한 사용자의 중요한 결정을, 관측 결과에 따라 다음 행동을 바꾸며, 확인 가능한 산출물까지 끝내는 작은 업무**다. 도메인 이름·도구 수·에이전트 수·3D 유무에는 가점을 주지 않는다. 보류도 정확한 결과일 수 있지만 모든 입력을 보류하는 것은 유용한 완료가 아니다.

예선 당시 후보 선택 질문을 계승하되 점수는 본선 진출에 맞춰 역산하지 않는다. 도구 탐색으로 후보를 찾는 것은 가능하지만, 기술명을 가리고도 사용자·실패·산출물·기존 대안 대비 필요성을 설명할 수 있어야 한다. 바이오처럼 도구가 많은 분야에 자동 가점을 주거나 Bio-3를 반드시 통과시키도록 기준을 조정하지 않는다.

당일 미션·필수 기술·반입 조건은 [행사 조건](../operations/event.md)을 확인한다. 사전 비교는 가능하지만 미공지 조건을 임의 통과시키거나 모든 후보의 점수를 0으로 만들지 않는다.

## 1. 점수보다 먼저 확인하는 관문

각 관문은 pass / fail / unknown과 근거를 기록한다. fail은 확인된 불가능·충돌, unknown은 아직 확인하지 못한 상태다.

| ID | pass에 필요한 증거 | fail일 때의 판단 |
|---|---|---|
| mission | 공개된 당일 미션·필수 조건에 핵심 과업이 부합 | 해당 미션 후보에서 제외 |
| access | 핵심 입력과 필수 도구의 접근·사용 조건을 확인; 실제 자료 최소 1건을 열어봄 | 허용된 대체 자료·도구로 바꾸거나 제외 |
| verify | 산출물의 성공·실패·올바른 보류를 팀이 주어진 시간 안에 구별하는 방법과 사례가 있음 | 검증할 수 있는 작은 결정으로 축소 |
| agency | 도구 결과가 다음 행동/질의/인자를 바꾸는 사례와 단순 기준선의 한계를 설명 | 일반 자동화로 재분류하거나 주제 재설계 |
| scope | 2명·7시간 안에 핵심 흐름과 검증이 가능한 작업 분해, 최소 범위와 포기할 기능이 있음 | 범위 축소 후 재평가 |

agency 통과는 LLM 우위의 실증이 아니다. 분기 표 하나만으로는 부족하고 **고정 규칙보다 유연한 판단이 필요한 이유**가 있어야 한다. 외부 변경이 필요한 후보는 테스트 환경·권한도 access의 일부이며, 읽기 전용 후보에는 외부 쓰기를 요구하지 않는다.

## 2. 100점 채점

각 항목을 0~4 정수 또는 null로 채점한다. 0은 확인된 부적합, 1은 주장 수준, 2는 구체적인 설계와 자료, 3은 아래 항목별 사례 확인, 4는 3을 포함한 비교·반례 검증이다. 자료 자체가 없으면 null이며 0과 구분한다. 조건을 모두 만족한 가장 높은 등급을 쓴다.

| ID / 항목 | 배점 | 2등급: 설계 근거 | 3등급: 선정에 쓸 근거 | 4등급: 강화된 근거 |
|---|---:|---|---|---|
| problem / 사용자 문제 | 20 | 사용자·실패 상태·산출물·쓸 결정을 명시 | 실제 입력에서 실패와 기존 수작업을 따라가고 영향·개선 지표 정의 | 사용자 확인 또는 실제 업무 자료로 비용/오류/시간의 개선 여지를 비교 |
| agency / 에이전트 이득 | 25 | 관측에 따른 행동 차이와 단순 기준선 명시 | 정상·변화·부족 사례에서 다음 행동이 달라지고 단순 기준선이 놓치는 정보/적응을 설명 | 같은 입력·도구·예산 비교에서 오류·누락·수작업·호출 중 사전 선택 지표의 이득 관측 |
| access / 자료·도구 준비 | 15 | 출처·입출력 계약·접근 조건 확인 | 대표 원자료를 직접 읽고 핵심 도구의 최소 요청/응답과 사용할 권한 확인 | 다른 입력과 실패 조건에서도 핵심 접근·제약·대체 경로 확인 |
| verify / 검증 가능성 | 15 | 종료 조건·검사법·금지할 과장 정의 | 정상·잘못된 완료·부족 사례를 원자료/독립 계산/상태로 구분 | 제품과 독립된 검사로 틀린 산출물을 거부하고 불필요한 보류도 판별 |
| nvidia / NVIDIA 기여 | 10 | 특정 구성요소의 입력·출력과 과업상 역할 명시 | 최소 호출/실행 기록에서 NVIDIA 구성요소가 핵심 경로에 기여함을 확인 | 제거·대체 비교로 기여 또는 선택의 실용적 이유를 확인 |
| scope / 시간 내 구현 | 10 | 작업 분해·담당 영역·핵심/포기 범위 정의 | 가장 위험한 연결을 짧게 확인하고 통합·검증·시연 시간을 확보 | 지연/실패를 포함한 최소 연결을 측정하고 일정 안의 대체 범위까지 확인 |
| inspect / 가치 확인 용이성 | 5 | 입력→행동→산출물→사용자 결정을 한 흐름으로 설계 | 대표 입력·근거 위치·성공/보류 차이를 따라갈 수 있음 | 비개발 동료가 흐름을 보고 무엇을 끝냈고 무엇이 미확인인지 정확히 설명 |

1등급은 해당 항목의 구상이 확인되지만 2의 구체성이 부족한 경우다. 0등급은 예컨대 명시적인 사용자 부재, 전부 고정된 불필요한 모델 호출, 접근 불가, 검증 불가능한 핵심 주장, 장식뿐인 NVIDIA 사용, 불가능한 일정, 실제 상태와 다른 결과 표시가 확인된 경우다. 결함이 없다는 추정만으로 점수를 주지 않는다.

일반적인 자료·도구와 NVIDIA의 역할은 서로 다른 질문이다. 같은 호출을 인용하더라도 access는 사용할 수 있는지, nvidia는 핵심 과업에서 무엇을 하는지를 판단한다. nvidia 4는 NVIDIA가 모든 대안보다 우월하다는 주장을 요구하지 않는다. 측정된 호환성·제공 자원·운영 비용 등도 선택 근거가 될 수 있다.

문제 20 + 에이전트 25를 가장 크게 둔 이유는 좋은 일반 앱과 좋은 에이전트 주제를 구분하기 위해서다. 자료·검증 30은 불가능한 주제가 미사여구로 통과하지 못하게 하고, NVIDIA 10·범위 10·확인 용이성 5는 본 대회와 시간 제약을 반영한다. 숫자와 아래 통과선은 실증된 최적값이 아니다.

## 3. 계산과 결정

확인 점수 S = Σ(배점 × 등급 / 4), 미평가 배점 U = Σ(null 항목 배점). `S / 100, 미평가 U, 가능 범위 S~S+U`를 함께 보고한다. 이 범위는 누락 점수의 산술 범위이며 신뢰구간·예상 점수가 아니다. 확인된 항목만으로 100점 재정규화하지 않는다.

판단 순서는 다음과 같다.

1. 관문 fail: 점수와 무관하게 제외 또는 축소. 어떤 변경이면 다시 평가할지도 적는다.
2. 핵심 관문 unknown 또는 U>0: 보류하고 가장 결정적인 확인 1개를 먼저 한다. 본선 조건만 미공지면 후보 우선순위는 잠정 비교할 수 있으나 최종 선정은 아니다.
3. 관문 전부 pass·U=0·S≥70·모든 항목≥2·problem/agency/verify≥3: 선정 후보. 곧바로 구현 완료나 품질 통과를 뜻하지 않는다.
4. 나머지는 축소·검증 후 재평가. S<50은 현재 범위에서 우선순위를 낮추되, 확인된 치명 관문 실패와 혼동하지 않는다.

70은 소규모 초기 검증을 마친 후보를 추리는 운영상 제안이다. 주제 구상만 있는 후보를 배제하기보다 저비용 확인 순서를 정하는 데 쓴다. 모델/API의 실제 호출은 별도 승인·예산 안에서만 하며 채점 요청 자체가 호출 승인은 아니다.

점수 차이 5점 이내는 사실상 동률로 보고 가장 큰 미확인 위험을 먼저 확인한다. 25점 항목의 등급 하나 차이가 6.25점이므로 소수점 순위에 의미를 부여하지 않는다. 가중치나 애매한 등급 하나를 조정했을 때 승자가 바뀌면 불안정한 선택으로 표시하고 비용이 작은 후보를 우선 검증한다.

## 4. 반례로 기준 점검

아래는 **논리 점검용 합성 사례**이며 실제 제품 평가나 대회 성적이 아니다. 등급 순서는 problem / agency / access / verify / nvidia / scope / inspect다. 실제 점수에는 각 등급의 증거가 필요하다.

| 사례와 가정 | 등급 | S / U / 가능 범위 | 판단 |
|---|---|---|---|
| 자료가 준비된 장애 원인 조사: 로그에서 모호한 원인을 좁히며 다음 조회를 바꾸고 근거 있는 조치안을 반환; 각 3등급 증거와 관문을 확보했다고 가정 | 3,3,3,3,3,3,3 | 75 / 0 / 75 | 선정 후보 |
| 같은 CSV를 항상 같은 순서로 변환: 규칙으로 끝나는 과업에 LLM 도구 선택만 추가 | 3,0,4,4,2,4,3 | 63.75 / 0 / 63.75 | agency fail; 일반 자동화로 재분류 |
| 화려한 다중 에이전트지만 데이터·정답에 접근했는지 미확인 | 2,3,null,null,3,1,4 | 43.75 / 30 / 43.75~73.75 | 상한이 높아도 access/verify unknown으로 보류 |
| 후보의 치료 효과 순위를 구조 출력만으로 확정한다고 약속; 이를 확인할 방법 없음 | 3,3,3,0,3,1,4 | 60 / 0 / 60 | verify fail; 구조 근거·누락 검토로 범위 축소 |

이 표는 장식·기술 수·잠재 점수로 치명적인 부적합을 덮지 않는지 확인한다. 잘 된 사례만 넣어 통과선을 조정하지 않는다. 범위를 축소하면 새 후보 버전으로 전체 항목을 다시 본다.

## 5. 당일 20분 후보 비교 절차

0~5분: 최대 3개 후보에 사용자·실패·산출물·가장 단순한 대안·동적으로 바뀌는 행동을 적는다. 5~10분: 핵심 자료 1건과 성공/실패/보류의 판정법, 관문을 확인한다. 10~15분: 두 사람이 같은 자료로 독립 채점하고 1등급 이상 차이를 근거로 조정한다. 15~20분: 우선 후보의 가장 위험한 연결을 확인할 작업·담당·중단 조건을 정한다. 실제 외부 실행이 오래 걸리면 20분 안에 완료했다고 가정하지 않고 보류한다.

후보 발굴에서는 가능하면 도구 목록에서 출발한 후보와 실제 업무 실패에서 출발한 후보를 함께 비교한다. 처음에는 기술명 없이 problem·agency·verify를 평가하고 그 뒤 NVIDIA 역할과 접근성을 본다. 문제 가치가 낮은 후보를 기술 친숙성으로 구제하지 않는다.

첫 구현에서는 정상·관측 변화·자료 부족 3입력을 준비한다. 규칙/단일 호출 기준선과 같은 도구·자료·예산으로 비교하고, 잘못된 완료·올바른 보류·과도한 보류·호출 수·지연을 따로 본다. 정확한 경로 하나를 강요하지 말고 허용되는 결과와 금지 행동을 검사한다.

핵심 API/자료 접근 실패가 해결되지 않거나, 모든 입력에서 같은 고정 경로가 충분하거나, 정답을 구분할 수 없으면 기능을 더 붙이지 말고 축소/교체한다. 한 번의 성공과 합성 입력만으로 일반 성능을 주장하지 않는다.

## 스킬과 채점표 사용

[$topic-rubric](../../.agents/skills/topic-rubric/SKILL.md)은 이 기준으로 평가한다. [채점표](templates/topic-scorecard.json)를 채워 `python3 scripts/score.py <채점표.json>`으로 계산한다. [JSON 기준](topic-rubric.json)은 이 문서의 계산용 사본이며 배점·등급·관문 변경 시 함께 갱신한다.

입력에는 후보명·범위 버전·평가 시각·미션 원문/미확인 상태·사용자/실패/산출물·기준선·상태별 다음 행동·자료/권한·검증법·NVIDIA 역할·일정/최소 범위·항목별 등급과 근거·관문 상태·다음 확인을 포함한다. 출력은 S/U/산술 범위·선정/보류/축소/제외 이유·가장 먼저 할 확인 1개다.

자동 검사는 배점 합 100, 등급 범위/중복/누락, null 전파, 관문 실패 우선, 최저 등급, 본선 조건 unknown의 잠정 판정, 위 합성 반례를 포함한다. 계산 검사와 실제 사용자 효용·심사 예측력·두 평가자의 일치도 검증은 별개다.

근거 수준은 claim(상한 1), design(2), observed(3), compared(4)다. 상한은 점수 부여가 아니며 위 항목별 조건을 모두 충족해야 한다. compared는 실제 업무 자료·독립 검사·대안 비교 등 각 4등급 조건의 확인을 뜻한다. 모든 채점 항목은 note, 숫자 등급은 evidence가 필요하고 null은 다음 확인을 적는다. 대상·범위 버전·환경·평가 시각·next_check도 필수다.

계산 결과의 candidate/hold/revise/exclude는 선정 후보/보류/축소 또는 재설계/미션 부적합 제외다. 미션 외 관문 실패는 revise로 내보내며 대체 범위가 없으면 평가자가 제외 이유를 설명한다. 미션만 unknown이고 나머지 선정 조건을 충족하면 hold와 provisional_candidate를 함께 표시한다. low_priority는 50점 미만의 현재 확인 점수 표시이며 자료 부족을 부적합으로 확정하지 않는다.
