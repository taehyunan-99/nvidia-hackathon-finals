# 2인 개발·로컬 시연 운영

본선은 사용자와 팀원 총 2명이 진행하며 미션은 당일 공개된다. 개발과 리허설은 본선 저장소에서 진행하고, 예선 프로젝트는 필요한 구현·디자인·실측 근거의 참고자료로 사용한다.

2026-10-07 공개된 [미션·필수 요건·공식 배점](mission.md)을 우선한다. **제출 마감은 17:20**이며 아래 기존 17:30 종료 계획의 마지막 10분은 제출 후 확인·발표 전환에 사용한다. 구두 안내상 오늘 평가는 새 미션의 결과를 대상으로 한다.

## 확정한 디자인

디자인 준비는 사용자와 확정했다. [80개 세부 기준과 상태 표시 묶음](../design/design-decisions.json)을 [디자인 스킬](../../.agents/skills/nvidia-ui/SKILL.md)·토큰·공통 컴포넌트 CSS·[대표 화면](../../design/playground.html)으로 재사용한다. 데스크톱 전용이며 모바일은 범위에서 제외한다.

진행·완료는 녹색, 보류는 황갈색, 실패는 빨강, 입력 전은 회색으로 표시하고 아이콘·설명·다음 행동을 함께 제공한다. 완료는 검증된 범위에만 사용하고 보류에서는 확인한 결과를 유지한다. `mock/replay/live`와 미검증을 구분한다.

미세 색상·간격 비교는 종료한다. 글꼴 제공 방식·표 장식·페이지 구조·다크 테마 등 미정값은 [디자인 안내](../design/README.md)에 구분하며 사용자 요청이나 실제 구현 필요 없이 다시 논의하지 않는다. 대표 화면은 주제·기능·배치 확정이나 실제 에이전트 실행 근거가 아니다.

로컬 개발·리허설에 더해 **외부 사용자가 직접 접속해 테스트할 배포 경로**를 준비한다. 공식 제출은 데모 URL 또는 실행 가이드를 허용하지만, 우리 팀은 AWS 배포를 희망한다. 큰 주제는 한국 문화, 필수 도구는 OpenShell이며 [보안정책 분석](../catalog/tools/openshell-security.md)·[배포 준비](../playbooks/openshell-deployment.md)를 따른다. Brev $500 등록은 확인했으며 구체적인 배치·사용 예산·접속 대상·유지 기간은 미정이다. 인스턴스 생성은 이후에 진행하고 현재는 미션·주제를 정리한다. 실제 모델·도구 호출과 결과 검증은 필요하며, mock/replay를 live 성공으로 대체하지 않는다.

두 구현 영역은 계약 합의 이후 병렬 진행한다. 프런트는 계약에 맞는 샘플 응답으로 먼저 연결하고, 에이전트가 준비되는 대로 실제 호출로 교체한다. 샘플 응답은 `mock`이며 실제 성공 근거가 아니다. 서비스 연결은 화면만이 아니라 에이전트를 호출하고 결과를 받는 경계까지 포함한다. 구체적인 계약·통합 담당·발표 담당은 당일 미션에 맞춰 정하며 개인에게 미리 배정하지 않는다.

## 유지할 기준

- 모델 호출은 [본선 공통 기본값](../playbooks/model-policy.md)을 재사용한다.
- 에이전트는 목표와 관측 상태에 따라 도구를 선택하고, 코드 검증기가 결과와 종료 조건을 확인한다.
- [승인된 루브릭](../evaluation/README.md)의 항목·가중치는 유지한다. 반복 평가는 `$agent-rubric`과 `$frontend-rubric`을 영역별로 사용한다.
- CI는 로컬 자동 검사+동료 검증+경량 원격 CI 보조가 기본 방향이다. 마지막 유효 검증 이후 누적 변경을 검사하며, 10분 초과는 일괄 차단 대신 검증 불충분과 대체 확인으로 처리한다.
<!-- prev: both 본문 유지 → 2026-10-07 사용자 요청으로 AGENTS 원본·CLAUDE @ 참조 적용. -->
- AGENTS 원본·CLAUDE 참조·repo 스킬 구조를 유지하고, 별도 작업 완료 보고서를 만들지 않는다.

## 구현 단계에서 확인할 조건

필수 기술·배점·제출물은 [미션 문서](mission.md)에 확정 범위를 정리했다. 사전 자료 반입 세부 규정, 실제 모델 권한·GPU 환경, 두 사람의 노트북 환경은 추가 확인이 필요하다. 실제 API 연결과 새 미션의 end-to-end 검증, CI의 검사 목록·성능 측정은 문서 준비만으로 완료되지 않는다.

개인별 정보 수집을 준비 논의의 선행 조건으로 삼지 않는다. 위의 진행 방향을 유지하고, 실제 구현 시 두 영역의 계약·로컬 실행 환경·통합 책임과 미션별 완료 조건을 정한다. CI의 실제 검사 항목과 시간은 구현 후 측정한다.

2026-10-06 사용자와 정리한 팀 운영 계획이다. 개발 시간은 2026-10-07 10:30–17:30, 한국 시간이며 마지막 1시간 30분은 발표·제출 준비와 마무리에 남긴다. 당일 미션·공식 제출 조건에 맞춰 조정하며, 개인별 담당과 미션별 완료 조건은 아직 확정하지 않았다. A/B는 작업 흐름을 나누기 위한 표기이며 특정 팀원에게 배정한 이름이 아니다.

| 15:00–16:00 | **공동:** 통합·교차 점검, 디테일 수정·안정화 | 공동 진행 |
| 16:00–17:20 | **공동:** 발표·제출 준비, 재시작 확인·시연 리허설, 최종 제출 | 공동 진행 |
| 17:20–17:30 | **공동:** 제출 링크·열람 권한 확인, 발표 전환 | 공동 진행 |

### 단계별 확인과 축소 기준

- **11:30:** Intent는 사용자·문제·완료 기준, PRD는 핵심 기능·제외 범위, Plan은 구현 순서·담당 흐름·검증 방법을 짧게 정리한다. 입력·출력·진행/완료/실패/보류 상태와 샘플 응답을 합의하고, 테스트 데이터 확보 가능성을 확인한다. 계약은 [기존 입출력 계약](../catalog/contracts.md)을 참고한다.
- **13:00:** 에이전트 틀과 화면 틀을 확인한다. 모든 핵심 도구가 이 시각까지 완성될 필요는 없으며, 실제 연결이 준비되는 순서대로 샘플 응답을 교체하고 15:00까지 구현·연동·검증을 이어간다.
- **15:00:** 실제 입력→에이전트의 도구 선택→실행→검증→화면 결과의 핵심 경로 1건 완주를 목표로 한다. 지연되면 입력 유형·도구 조합·산출물·부가 화면을 줄이되, 판단·결과 검증·실패/보류 표시는 유지한다. 공동 점검에서는 정상·자료 부족·실패 사례와 화면의 근거·상태 일치를 확인한다.
- **16:00:** 새 기능 추가를 멈추고 핵심 결함 수정과 발표·제출 준비에 집중한다. 로컬 재시작과 대표 시연을 확인하고, 검증하지 못한 범위와 한계를 정리한다.
- **17:20:** 공식 공지에 맞춰 저장소·데모 정보·발표자료 제출을 완료한다. 이후 변경이 평가에 포함된다고 가정하지 않는다.

### 테스트 작업이 먼저 끝났을 때

담당 B는 실패·경계 입력 추가, 실제 결과와 화면의 근거 표시 대조, 대표 시연 데이터·기대 결과 선정, 재실행·복구 확인을 진행할 수 있다. 우선순위는 공동 점검에서 드러날 결함을 줄이는 것이다.

사용자가 확인한 발표 길이는 [5분](event.md)이다. 실제 라이브 분석이 발표 시간에 비해 오래 걸리는 경우에만 [시연용 워크플로우 압축](../playbooks/rehearsal.md#시연용-워크플로우-압축--조건부-검토)을 검토한다. 압축 구현을 기본 할 일이나 완료 조건으로 두지 않는다.

공식 반입·필수 기술·자원·제출 조건은 [행사 안내](event.md)를 따른다. GPU가 필요할 때의 준비·접속·종료 절차는 [Brev 당일 가이드](../playbooks/brev-event-guide.md)를 확인한다.
