# 본선 미션과 제출 요건

기준일: **2026-10-07, 한국 시간**. 사용자가 전달한 슬랙 공지, 발표 PDF 17쪽, 녹취록 2개와 챌린지 저장소를 대조한 미션 해석 원본이다. 공식 요구, 구두 보충, 팀의 구현 제안과 미확인 사항을 구분한다. 서비스 주제 선정·구현·인스턴스 생성은 이 문서 작성에 포함하지 않았다.

구현 중·제출 전 반복 점검은 [$submission-check](../../.agents/skills/submission-check/SKILL.md)를 사용한다. 필수 요건별 실제 근거를 확인하며 결과 파일을 자동 생성하거나 외부 제출을 실행하지 않는다.

## 1. 먼저 확정할 핵심

**한국 문화·역사·지역·여행의 복합 맥락을 이해해 실제로 쓸 수 있는 결과를 만드는 에이전트와, 그 에이전트가 OpenShell 안에서 권한 경계를 지키는 실행을 함께 보여주는 과제다.**

| 구분 | 요구 | 근거 |
|---|---|---|
| 서비스 미션 | 여러 자료와 사용자 상황을 이해하고 맥락·신뢰성을 판단해 유용한 결과 생성 | 슬랙 §1, PDF p.4 |
| 필수 기술 | 제출 프로젝트에 **NVIDIA OpenShell 구성요소 포함** | 슬랙 필수 요건, PDF p.12 |
| 데모 | 실제 동작하는 결과와 확인 가능한 실행 경로 | 슬랙 §1, PDF pp.4·13 |
| 공통 테스트 | 제공 자료를 처리하면서 허용/금지 경계를 유지 | 슬랙 §2, PDF p.5 |
| 제출 마감 | **오늘 17:20까지 발표자료·데모코드 제출** | 사용자가 전달한 최신 슬랙 공지 |
| 발표 | **팀별 총 5분**, 실제 데모·영상 로딩 포함 | PDF p.13, 저장소 README |

**두 축의 구분:** 공통 테스트 자료를 잘 처리하는 것만으로 서비스의 실용성과 독창성이 완성되지는 않는다. 반대로 문화 서비스의 결과가 좋아도 OpenShell이 빠지거나 실제 실행 경계를 증명하지 못하면 요구를 충족하지 못한다. 녹취 2의 01:47–04:38, 16:05–17:03, 24:24–27:10이 이 구분을 반복해서 설명한다.

## 4. Creative Use-case 미션의 의미

### 무엇을 해결해야 하는가

주제 범위는 한국의 문화·역사·지역·여행이다. 사용자가 처한 상황과 서로 다른 자료의 맥락을 함께 이해하고, 현재 요청에 적합한 정보를 선별해야 한다. 단순히 관련 문서를 찾아 나열하거나 장소를 추천하는 것을 넘어 **판단을 거친 실행 가능한 결과**가 필요하다. [S §1, P p.4]

| 관점 | 미션에서 요구하는 방향 | 구현 관점의 해석 — 팀 제안 |
|---|---|---|
| 사용자 상황 | 요청과 조건을 이해 | 방문 날짜·대상·제약·허용 행동을 작업 상태로 보존 |
| 자료의 맥락 | 서로 다른 시점·관점·대상을 구분 | 출처, 작성일과 적용일, 사실/홍보/추정, 대상 일치 여부 비교 |
| 신뢰성 판단 | 필요한 유효한 정보를 선별 | 채택·배제·충돌·확인 필요 이유를 결과와 연결 |
| 에이전트 행동 | 목표에 따라 계획·도구 활용 | 관측 결과에 따라 다음 도구·수정·보류·종료를 선택 |
| 유용한 결과 | 실제 사용 가능한 수준 | 단순 요약보다 사용 목적·조건·근거·남은 확인 사항을 갖춘 산출물 |

표 오른쪽은 구현 제안이지 추가 공식 배점이나 정답 형식이 아니다. ‘정확함’은 모르는 내용을 확정하는 것이 아니라 자료가 부족하거나 충돌하면 그 범위를 드러내는 것을 포함한다.

### 주제를 어디까지 자유롭게 정할 수 있는가

T2 24:24–27:10은 **제공 데이터로 제품 기능을 한정할 필요가 없고**, 공통 파일은 OpenShell 접근과 판단을 확인하기 위한 가벼운 테스트 자료라고 설명한다. 역사·문화·여행 외 한국 관련 연예인 등의 예시도 구두로 언급된다. 구체적인 서비스는 우리 팀이 정하되, 공식 대주제와 맥락·신뢰성 판단 요구에 연결해야 한다.

## 6. OpenShell 공통 테스트

### 디렉터리 계약

| 경로 | 주최 측 역할 | 정책 설계 해석 |
|---|---|---|
| `/hackathon/input` | 참고·활용 가능한 자료 | 읽기는 허용하되 내용의 신뢰·관련성을 판단; 원본 쓰기는 허용하지 않는 구성을 제안 |
| `/hackathon/output` | 결과물 생성 | 필요한 읽기·쓰기만 허용하고 최종 산출물을 여기에 저장 |
| `/hackathon/restricted` | **접근 금지** | 읽기·쓰기·다른 경로를 통한 접근을 허용하지 않음 |
| `/hackathon/secrets` | **접근 금지** | 검색·출력·모델 전송 등 모든 간접 노출도 방지 |

근거: S §2, P p.5, T2 02:46–04:38·08:26. **금지 파일을 삭제해서 접근 실패를 만드는 것은 보안정책 검증이 아니다.** 파일을 포함한 상태에서 접근을 차단하라는 구두 지시가 T2 03:42에 있으므로 패키지를 보존한 배치·검증을 준비한다.

저장소 내부 상대 경로 `hackathon/input`와 실행 환경의 절대 경로 `/hackathon/input`를 매핑해야 한다. 기존 조사 문서의 `/workspace` 합성 예제는 설치 확인용이며 공식 테스트 경로의 대체물이 아니다.

### 무엇을 시험하는가

- **정상 업무:** 허용 자료를 읽고 사용자 조건을 반영해 output에 실제 결과를 만든다.
- **정보 판단:** 오래된 기록, 상충 주장, 동명이인, 홍보성 정보, 무관한 키워드 자료를 구별한다.
- **실행 경계:** 금지 파일·미승인 목적지·외부 행동 시도가 실제 runtime에서 막히는지 확인한다.
- **권한의 의미:** 초안 요청을 이메일 발송·게시·예약·결제·외부 업로드 권한으로 확대하지 않는다.
- **변화 대응:** 발표 중 추가 조건·예외 요청에도 새 입력을 처리하고 안전 경계를 유지한다.

공통 결과물에 정해진 단일 형식은 없다. 추가 조건은 P p.5와 R README에 명시돼 있고, T2 03:42는 심사자가 사용자 관점에서 직접 요청할 수 있다고 설명한다. 특정 고정 입력·정답 문자열만으로 성공을 만들지 않는다.

### 증명 방법 — 팀 제안

정상 처리 결과, 채택·배제한 출처와 이유, 실제 도구 결과, 적용 policy, 금지 행동의 거부 근거를 연결해 보여준다. **모델이 ‘접근하지 않았다’고 말한 것과 운영체제/runtime이 실제로 막은 것은 다르다.** 파일 부재·연결 장애·API 인증 실패도 정책상 거부와 구분한다.

실제 요청을 처리하는 프로세스와 모든 관련 파일/네트워크 도구가 sandbox 경계 안에 있어야 한다. 호스트의 별도 검색기가 restricted를 읽어 결과만 sandbox로 전달한다면 의도한 경계를 우회하게 된다. 승인되지 않은 외부 행동을 도구 미제공·호출 검증·OpenShell 정책의 해당 경계에서 제어한다.

## 7. 제공 저장소 분석

### 패키지의 성격

기준 commit의 트리는 **업무 구현 코드가 아니라 공통 테스트용 자료 패키지**다. README·TASK·MANIFEST·데이터는 있지만 앱 entrypoint·Dockerfile·OpenShell policy는 확인되지 않았다. 따라서 clone만으로 에이전트가 실행되거나 안전정책이 설치되지는 않는다.

루트에는 `.gitignore`, `README.md`, `TASK.md`, `MANIFEST.csv`가 있다. `input`은 20개 파일, `output`은 `.gitkeep`, `restricted`와 `secrets`는 각각 3개 파일이다. `MANIFEST.csv`는 `path,bytes,sha256` 형식의 파일 목록이다. 이번 분석에서는 **금지 두 디렉터리는 트리의 존재만 확인하고 내용은 열지 않았다**. 입력 자료는 모두 가상 데이터라는 README의 고지를 따른다. 실제 인물·관광지·의료정보·자격증명으로 취급하지 않는다.

## 8. 공식 심사 배점

| 항목 | 배점 | 공지의 평가 방향 | 준비할 근거 — 팀 제안 |

| 실용성·산업적 가치·혁신성 | **20** | 적용 가능성·산업 영향·독창성 | 구체적인 사용자 문제와 결과의 사용 가치 |

| 합계 | **100** | 심사위원 영역 90 + 동료평가 10 | 아래 계산 불확실성 참고 |

근거: S §3, P p.12. 슬랙은 최종 점수를 **심사위원 평균 점수 + 동료 평가 점수**로 설명한다. 위 표는 배점 구조를 정리한 것이며, 동료평가의 원득표·순위→점수 환산이나 동점 처리를 자체 구현하지 않는다.

슬랙의 순위별 `10, 9, 8, 7, 6, 5, 4` 설명, PDF의 `20, 18, 16, 14, 12, 10, 8` 문구, 녹취의 10팀 최하위 1점·공동순위 설명 사이에 차이가 있다. **동료평가 총 10점과 자기 팀 투표 금지는 공지대로 적용하고, 세부 산식은 확인 필요**다.

저장소의 `topic-v1`, `agent-v2`, `frontend-v2`는 내부 설계·검증 도구이며 이 공식 100점표와 다르다. 이번 정리로 내부 JSON 가중치·채점 코드를 바꾸거나 내부 점수를 공식 예상 점수로 환산하지 않았다. [내부 평가 진입](../evaluation/README.md)

README에는 프로젝트 소개, 환경 설치·실행 방법, 데모 확인 방법, 평가/검증 절차, policy 파일 경로, 주요 접근제어와 각 권한의 이유, 외부 API/서비스와 허용 범위를 넣는다. PDF의 training instructions 항목은 학습이 없다면 **‘학습 미수행/해당 없음’**으로 분명히 적고 사용 모델·추론 연결은 설명한다. 학습을 했다면 재현 방법이 필요하다. [P p.13, T2 18:54, R README]

지정 Slack 제출 채널에는 **팀명·프로젝트명 / 저장소 URL / 데모 URL 또는 실행 방법 / 발표자료 / 필요한 참고사항**을 함께 게시한다. 실제 제출 채널이 공지 채널과 같은지는 확인한다. 마감 이후 변경은 평가에 반영되지 않을 수 있으므로 제출 시점 코드·데모·자료를 일치시킨다. [저장소 제출·발표 안내](https://github.com/seriousran/k-culture-openshell-challenge/blob/714e2e8d32f9b77e763a2458ca11b1270e80abf6/README.md)

공식 요구는 **공개 웹 배포만 허용하는 형태가 아니라 데모 URL 또는 실행 방법**이다. 다만 우리 팀은 사용자가 직접 접속해 테스트할 배포를 원하므로 AWS 등 외부 접속 경로를 준비하는 방향을 유지한다. localhost 주소만 전달하거나 실행 의존성·권한을 설명하지 않은 가이드는 검증 가능한 접근 경로로 보기 어렵다. [P p.13, T2 10:24]

‘오픈실/오픈셀/오픈제/오픈체/오픈셰’ 등 반복 표현은 주변 문장과 슬라이드가 같은 제품을 가리키는 구간에서만 **OpenShell**로 정규화했다. ‘리틀리/이드미’는 제출 설명의 README, ‘브래브/브래그/그래블’은 환경·크레딧 문맥의 Brev로 이해했다. 모호한 인명·행사 규모·투표 숫자·불완전 문장은 새 사실로 복원하지 않았다. 원문 TXT는 그대로 보존했다.

## 12. 팀의 다음 결정과 실행 경계

2026-10-07 후속 사용자 인터뷰에서 **한국 가족이 관심 분야의 문화체험을 발견·비교·선택하는 과업**을 MVP로 정했고 참여조건 확인은 추천 신뢰성을 뒷받침한다. [제품 정의](../product/README.md)가 현행 범위 원본이며 아래 절차의 주제 탐색은 그 결정 이전의 단계다. 지도·이동·영어·통역 검색은 선택 기능이고 OpenShell·공통 테스트는 필수다.

1. **주제:** 사용자 한 종류와 명확한 실패 상황을 고르고, 에이전트의 판단이 바꾸는 결과를 정의한다.
2. **계약:** 제품의 입력·출력·완료/보류 기준과 공통 테스트의 `/hackathon` 처리 경로를 함께 정한다.
3. **최소 실행:** 실제 도구를 OpenShell 안에서 실행하고 정상 작업과 금지 접근을 각각 확인한다.
4. **제출 준비:** 실제 데모 접근·README·policy·발표자료를 17:20 전에 같은 코드 기준으로 준비한다.

초기 조사에서는 인스턴스 생성을 보류했다. 이후 기존 AWS에 [합성 프런트](../playbooks/frontend-deployment.md)를 공개했고 기존 Brev VM에서 [연결 시험](../playbooks/aws-brev-deployment.md)과 [최소 보안 하네스](../playbooks/openshell-harness.md)를 검증했다. 현재 남은 작업은 실제 패키지 배치·에이전트/결과 회수 연결·최종 정책 재검증이며, 추가 자원 생성·예산 확대·외부 제출·팀원 메시지 전송은 별도 요청 범위다.

어떤 주제를 택하더라도 ‘공통 테스트 통과’와 ‘쓸모 있는 문화 서비스’를 별도의 완료 조건으로 확인한다. 제약과 배점을 반영한 후보 비교는 [주제 선정 기준](../evaluation/topic-selection.md)에서 이어간다.
