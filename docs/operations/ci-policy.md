# 해커톤 CI 운영 원칙

이 문서는 합의한 검사 선택·시간 예산·결과 해석 기준이다. 본선 주제·코드·실행 환경이 정해지기 전에는 최종 검사 목록이나 소요 시간을 확정하지 않는다. 실제 CI 설정은 이 원칙을 바탕으로 첫 구현의 실행 시간을 측정한 뒤 구성한다.

## 핵심 결정

- 본선은 사용자와 팀원 **총 2명**이 참여한다. **로컬 자동 검사 + 동료 교차 검증 + 짧은 원격 CI 보조**를 기본 운영 방향으로 삼는다.
- 작성자는 로컬 검사를 거친 작은 기능 단위를 공유하고, 원격 CI를 기다리는 동안 독립적인 다음 작업을 진행할 수 있다.
- 원격 CI는 빌드·타입·핵심 계약·짧은 회귀 검사 위주로 **1~3분을 목표**로 구성한다. 실제 항목·소요 시간은 본선 첫 구현에서 측정한다.
- 비싼 검사는 변경 영향과 통합 필요에 따라 별도 선택한다. 원격 CI를 없애거나 모든 검증을 팀원에게 떠넘기는 방식으로 확정하지 않는다.
- 최종 확인도 **5~7분을 설계 목표로, 10분을 동기적으로 기다리는 상한**으로 둔다. 실측 전 성능 보장은 아니다.
- 10분 초과를 이유로 일괄 실패 처리해 모든 작업을 자동 차단하지 않는다. 명확한 결함과 시간 초과·환경 장애를 구분한다.
- 마무리 단계라는 이유만으로 전체 CI를 새로 실행하지 않는다. 마지막 유효 검증 이후의 누적 변경과 의존관계를 기준으로 검사한다.
- 미검증을 통과로 바꾸거나 이전 버전의 통과를 현재 버전의 결과로 표시하지 않는다.

## 두 명의 개발·교차 검증

각자 구현 영역을 맡고 작은 기능 단위로 서로 검증한다. 한 명을 상시 검증 전담으로 고정하지 않는다. 구체적인 개인별 담당과 교대 방식은 역할 분담 논의에서 정한다.

| 단계 | 작성자 | 검증자 / 공통 확인 |
|---|---|---|
| 공유 전 | 변경 부분의 로컬 자동 검사 | 사람이 수동으로 빌드·타입 오류를 찾는 부담을 줄임 |
| 공유 | 요청된 작업 브랜치에 push, commit SHA·변경 목적·실행 방법·기대한 결과 전달 | 해당 버전에서 검증; 다른 변경과 섞지 않음 |
| 검토 | 원격 CI가 실행되는 동안 독립 작업 가능 | 실제 사용 흐름·결과 타당성·정상/변화/실패 시나리오 확인 |
| 수정 | 재현된 문제를 수정하고 새 commit의 영향 범위 검사 | 재현 방법·기대/실제 결과·영향도를 짧게 전달 |
| 통합 | 양쪽 변경을 합친 대상 준비 | 합쳐진 코드의 대표 흐름 확인; 각 브랜치의 개별 통과만으로 통합 성공을 가정하지 않음 |

개발 브랜치 공유, main 통합, 배포는 서로 다른 판단이다. 원격 실행 대기 때문에 모든 개발을 멈추지는 않지만 발견된 결함과 검증 불충분 상태를 숨긴 채 통합 완료로 처리하지 않는다. 검사 결과와 검토 내용은 기존 PR/대화/CI 결과로 전달하고 별도 완료 보고서를 만들지 않는다.

## 경량 원격 CI의 역할

공통 환경의 설치·빌드·타입·핵심 계약/회귀를 보조 확인한다. 동료는 자동화하기 쉬운 검사를 반복하는 대신 동작의 의미와 사용자 경험을 확인한다. 로컬과 CI는 같은 검사 명령을 사용한다.

첫 구현에서 경량 CI의 실제 실행/대기 비용과 잡아낸 오류를 확인한다. 원격 실행이 제공하는 이득보다 비용이 크면 두 사람이 로컬 대체 범위와 통합 검증 방법을 합의해 더 줄일 수 있다. 단순히 늦다는 이유로 현재 설정을 자동 비활성화하거나 보호 규칙을 우회하지 않는다.

## 검사 선택

프런트 수정도 코드 변경이다. 파일 확장자나 작업 단계보다 **바뀐 동작과 영향받는 영역**을 기준으로 선택한다.

| 변경 | 우선 수행할 검사 | 확대 조건 |
|---|---|---|
| 문구·일반 문서 | 링크·형식·관련 자료의 일관성 | 실행에 쓰이는 프롬프트·설정·스키마·데이터가 바뀌면 해당 런타임 검사 포함 |
| 프런트·스타일 | 빌드·타입·변경 화면/컴포넌트와 관련 상태 검사 | API 계약·공유 타입·결과 해석까지 바뀌면 연결 검사 포함 |
| 에이전트·업무 로직 | 변경 규칙·도구 선택·반환값 검증·실패/보류·종료 조건 | 호출 순서·공통 상태·외부 도구 연결에 영향을 주면 통합 검사 포함 |
| API·DB·worker·공통 계약 | 영향받는 소비자/생산자와 핵심 흐름의 통합 검사 | 공유 경계가 넓거나 영향 판단이 불명확하면 범위 확대 |
| 의존성·빌드·Docker·환경·CI 설정 | 해당 구성의 설치/빌드·기동·대표 흐름 | 기존 실행 환경의 검증 결과를 그대로 재사용할 수 없으면 관련 검사 재실행 |
| 변경 없음 | 유효한 기존 검증 결과 활용 | 기준 버전·입력·설정·검사 자체가 달라졌거나 결과가 불완전하면 재확인 |

`docs/` 전체를 검사 제외 대상으로 삼지 않는다. 예선 저장소처럼 문서 경로에 실행 코드·계산 자료·스키마가 들어갈 수 있다. 분류되지 않은 변경은 검사 누락 대신 보수적인 관련 검사로 연결한다.

## 비교 기준과 누적 변경

직전 커밋이 아니라 **검사를 완료한 기준 버전부터 현재까지의 누적 차이**를 사용한다. 다른 팀원의 병합 변경과 미커밋 변경도 실제 검사 대상에 포함한다.

기존 결과를 재사용하려면 최소한 대상 코드 버전(미커밋 작업이면 변경 내용 식별), 실행한 검사 범위, 관련 입력·의존성·설정, 실행 환경/모드와 결과를 확인할 수 있어야 한다. 결과는 기존 CI 실행 정보나 필요한 최소 로컬 실행 정보로 확인하며 별도의 작업 완료 보고서를 만들지 않는다.

기준 버전이 없거나 현재 이력과 연결되지 않거나 검사 범위가 불명확하면 '이미 검증됨'으로 처리하지 않는다. 필요한 검사를 실행해 기준을 확보한다. 영역별 기준을 사용한다면 이번에 확인한 영역만 갱신하며, 일부 검사 통과로 저장소 전체를 검증 완료로 올리지 않는다.

예: 로직을 수정했지만 아직 검증하지 않은 상태에서 CSS만 추가 수정했다면, CSS 검사와 미검증 로직 검사가 모두 남는다. 로직과 그 의존관계가 유효하게 검증된 뒤 CSS만 바뀌었다면 관련 프런트 검사만 수행한다.

## 10분에 도달했을 때

10분은 대기·재판단 시점이다. 단순한 `timeout-minutes: 10` 설정만으로 이 운영 원칙이 구현되지는 않는다.

| 관찰 결과 | 해석 | 다음 행동 |
|---|---|---|
| 빌드 실패·잘못된 결과·계약 위반 등 재현 가능한 결함 | 해당 변경의 검증 실패 | 해당 결함을 수정하고 관련 검사를 재실행 |
| 시간 초과·runner/네트워크 장애 | 검증 불충분 | 완료된 결과를 유지하고 미완료 검사를 식별; 현재 변경의 핵심 검사를 로컬 또는 축소된 별도 실행으로 확인 |
| 선택한 검사 전부 통과 | 그 버전·범위의 검증 통과 | 남은 영향 영역이 없는지 확인 후 다음 작업 |
| 검사 일부만 통과 | 부분 검증 | 나머지를 통과로 취급하지 않고 별도 실행·범위 조정 여부 판단 |

남은 검사는 자원·목적에 따라 별도로 계속하거나 범위를 줄여 다시 실행한다. 관련 없는 작업까지 모두 멈추지는 않되, 확보하지 못한 핵심 근거가 필요한 기능을 검증 완료로 선언하지 않는다. 시간 초과만으로 현재 변경을 잘못된 코드라고 단정하지도 않는다.

GitHub의 실제 job timeout 상태와 위의 '검증 불충분' 해석은 별개다. 필수 확인 결과를 항상 반환하는 구조와 별도 무거운 검사를 구분하고, 최종 판정은 선택한 검사 결과를 확인하도록 구성한다. 로컬 대체 검증이 GitHub 필수 검사 통과를 자동으로 대신하지는 않으며, 보호 규칙을 임의로 우회하지 않는다.

## 지금 준비할 하네스의 범위

복잡한 검사 플랫폼보다 다음의 작은 계약을 우선한다.

1. 변경 영향 → 수행할 검사 목록을 결정하는 규칙.
2. 로컬과 CI에서 공통으로 사용하는 검사 명령.
3. 결과를 `통과 / 결함 발견 / 검증 불충분 / 미실행`으로 구분하는 방식.
4. 어느 코드·입력·설정·검사 범위의 결과인지 확인하는 최소 정보.

에이전트 검사에서는 정상·변화·자료 부족/실패 입력, 허용 도구, 반환값의 형식/근거, 종료·호출 상한을 우선한다. 고정 모델 응답과 가짜 시계로 분기·재시도 처리를 빠르게 검사하되, 실제 모델/API 검증과 구분한다.

대규모 데이터 평가·전체 계산 재현·실제 모델 반복 호출은 별도 경로로 둔다. 해당 계산/연결을 수정했다면 필요한 결과까지 확인하며, 빠른 CI 통과만으로 전체 모델 품질이 검증됐다고 주장하지 않는다.

## 구현할 때 확인할 것

독립 검사의 병렬 실행, 적절한 대표 입력, 의존성/이미지 캐시, 같은 PR의 오래된 실행 취소 등을 실측에 따라 선택한다. 캐시가 없는 실행 시간도 측정한다. 검사 통과 자체를 캐시해 변경된 코드의 실행을 생략하지 않는다.

필수 workflow 전체를 경로 필터로 생략하면 검사가 Pending에 남을 수 있으므로, 변경 판별·최종 판정은 항상 수행하고 관련 job을 선택하는 구성을 검토한다. 집계 job은 실패한 의존 job 때문에 자신도 생략되어 실패를 숨기지 않도록 설계한다. [GitHub 필수 검사 안내](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)

구체적인 명령·경로 분류·필수 검사·병렬화·캐시 설정은 본선 스택이 정해진 뒤 결정한다. 이 문서는 검사 운영 원칙이며 당일 작업 스케줄이나 CI 구현 완료 보고서가 아니다.
